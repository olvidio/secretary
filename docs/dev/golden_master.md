# Golden master (Fase 0 del plan de ampliaciones)

`tests/integration/GoldenMasterTest.php` es la red de seguridad antes de tocar el
modelo de datos (ver `docs/dev/plan_ampliaciones.md`). Importa `moviments2026.xlsm`
contra una base Postgres vacía y aislada, y compara la salida de **todos** los casos
de uso de consulta con los ficheros de referencia de `tests/golden/*.json`. A partir
de ahora, ninguna fase puede cambiar esos ficheros sin documentar y justificar la
diferencia (la única excepción prevista es la Fase 3, que debe listar explícitamente
qué cambia y por qué).

## Por qué existe

La Fase 3 (partida doble) reescribe `apuntes`, `SignoTesoreria`, `CalcularSaldos`,
`CerrarMes` e `ImportarExcelSecretario`: es la fase de mayor riesgo del plan. El golden
master es lo único que permite comprobar, mecánicamente, que una refactorización tan
grande no ha alterado ni un céntimo (o que, si lo hace, es exactamente el cambio
esperado y documentado).

## Qué cubre el volcado

Un fichero JSON por informe/consulta, todos bajo `tests/golden/`:

| Fichero | Caso de uso / origen |
| --- | --- |
| `importacion.json` | Resultado de `ImportarExcelSecretario::ejecutar()` (recuentos) |
| `configuracion.json` | `ObtenerConfiguracion` (configuración importada del Excel) |
| `personas.json` | `ListarPersonas` |
| `conceptos_p.json`, `conceptos_g.json` | `ListarConceptos('P'\|'G')` (incluye los conceptos 72-79 renombrados por la importación de entidades) |
| `presupuesto_p.json`, `presupuesto_g.json` | `PresupuestoRepository::listar()`, ordenado explícitamente por `concepto_codigo` |
| `resumen_613_p.json`, `resumen_613_g.json` | `ObtenerResumen613::ejecutar('P'\|'G')` |
| `e37.json` | `ObtenerE37::detalle(null)` — el listado completo (hoja "E 37") |
| `e37_resumen.json` | `ObtenerE37::resumen()` — el agregado por persona (hoja "E 37 Resumen") |
| `saldos.json` | `CalcularSaldos::ejecutar(null)` — caja, banco, saldo A y saldo por persona a fecha de cierre |
| `arqueo.json` | Último arqueo P y G (`ArqueoRepository::ultimo`); hoy es `null` en ambos porque la importación no crea arqueos |
| `apuntes_agregado.json` | **No es un informe de la aplicación.** Es una firma de control: número total de apuntes, y sumas agrupadas por (cuenta, origen), (cuenta, concepto) y (cuenta, iniciales), calculadas con una consulta SQL propia del test. Es lo que detectará si la migración a partida doble (Fase 3) deja de contar o de sumar algo — incluidos los pares de traspaso 41/42, cuyo recuento debe pasar de "dos apuntes" a "un asiento" de forma consciente. |

El test usa directamente las clases de aplicación/dominio existentes
(`ObtenerResumen613`, `ObtenerE37`, `CalcularSaldos`, `ImportarExcelSecretario`,
`SchemaInstaller`, los repositorios `Pdo*Repository`) tal como las llama la
aplicación; no duplica su lógica.

## Aislamiento de la base de datos

El test **nunca** toca la base `secretario` de desarrollo. Usa una base aparte,
`secretario_test`, en el mismo servidor Postgres del stack (`127.0.0.1:5455`,
usuario `secretario`). Si no existe, la crea (el rol `secretario` tiene
`CREATEDB`); si existe, borra y recrea el *schema* `public` antes de instalar el
esquema y ejecutar la importación. Esto es necesario porque la migración inicial
(`migraciones/0001_inicial.sql`, ver `docs/dev/migraciones.md`) usa
`CREATE TABLE IF NOT EXISTS` y las columnas `GENERATED BY DEFAULT AS IDENTITY`
seguirían avanzando entre ejecuciones si no se partiera de cero: sin este borrado,
los `id` volcados en el JSON no serían reproducibles entre ejecuciones.

Desde la Fase 1 (`docs/dev/plan_ampliaciones.md`), el mecanismo de aislamiento (crear
la base si falta, dejar el esquema `public` vacío) está factorizado en el trait
`Tests\Soporte\BaseDeDatosAislada`, compartido con `SchemaInstallerTest` y
`MigrationRunnerTest`.

No hace falta ninguna acción manual: `composer test` crea y limpia
`secretario_test` por sí solo. Si se quiere inspeccionar a mano:

```bash
PGPASSWORD=secretario psql -h 127.0.0.1 -p 5455 -U secretario -d secretario_test
```

## Cómo regenerar el golden master

Solo tras un cambio **intencionado y documentado** en un informe:

```bash
GOLDEN_UPDATE=1 vendor/bin/phpunit tests/integration/GoldenMasterTest.php
```

Esto reescribe todos los ficheros de `tests/golden/*.json` y el test pasa (no
compara, solo genera). Ejecuta el test una segunda vez sin la variable para
comprobar que el resultado es estable, y revisa el `git diff` de `tests/golden/`
antes de dar el cambio por bueno.

Si los ficheros no existen todavía (por ejemplo, en un checkout nuevo), el test los
genera automáticamente la primera vez, sin necesidad de `GOLDEN_UPDATE`, y pasa.

## Fragilidades detectadas en los informes actuales (no corregidas en esta fase)

Esta fase **no refactoriza nada**; se limita a fotografiar el comportamiento actual.
Quedan anotadas aquí para cuando se aborde la Fase 3 u otra revisión:

- **`PresupuestoRepository::listar()` no hace `ORDER BY`.** SQL no garantiza el orden
  de filas sin ordenación explícita. Hoy no afecta a los informes porque
  `ObtenerResumen613` indexa el resultado por `concepto_codigo` (un mapa, no una
  lista), pero el test ordena explícitamente antes de volcar para no depender del
  planificador de Postgres.
- **`pct` en `Calculadora613::lineas()` y en los totales de `ObtenerResumen613` es un
  `float` nativo** (división de dos importes), no un string. `json_encode` con
  `serialize_precision = -1` (el valor por defecto de PHP) es determinista para un
  mismo valor en la misma plataforma, así que no ha dado problemas de reproducibilidad
  en las pruebas realizadas, pero es una excepción a la regla "los importes se
  guardan y comparan como string" y merece revisión si algún día cambia de máquina o
  de versión de PHP el `serialize_precision`.
- **La importación no crea arqueos.** `ImportarExcelSecretario` no lee las hojas
  "Arqueo P"/"Arqueo G" del Excel, así que `arqueo.json` refleja `null` en ambas
  cuentas. No es un bug de esta fase, pero conviene saber que el golden master no
  está probando el camino de guardado de arqueos.
- **Timestamps excluidos deliberadamente.** `apuntes.created_at`,
  `configuracion.updated_at` y el hash de `usuarios.password_hash` (con sal
  aleatoria) dependen del reloj o de aleatoriedad y no se vuelcan: el test solo lee a
  través de los métodos `toArray()` de las entidades / casos de uso, que ya los
  omiten. Si en el futuro se añade un informe que exponga alguno de estos campos,
  habrá que excluirlo explícitamente del volcado o el golden master dejará de ser
  reproducible.
- **Nada de lo anterior obligó a tocar código de producción.** El test conecta
  directamente a `secretario_test` con sus propias credenciales PDO y construye los
  casos de uso con `new` (mismo cableado que hace `src/shared/config/dependencies.php`
  vía PHP-DI, pero sin arrancar `Kernel::boot()` — evita sesiones HTTP y rutas, que no
  hacen falta para este test).
